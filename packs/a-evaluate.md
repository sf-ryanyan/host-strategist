# A · 为屋主做房源评估（深度）

目标：准确地告诉用户——这套房能不能做 Airbnb、每月能赚多少（低 / 预期 / 高）、成本多少、带家具 vs 不带家具、有哪些风险，以及用户自己能赚多少。然后给用户一份可以直接交给屋主的单页报告和沟通话术。准确比速度重要：先调研、注明来源、用脚本计算、再自查。

同时阅读：`settings.md`、`ref/south-bay.md`（或用户自己的 `ref/market-*.md`）。使用 `scripts/str_model.py` 和 `scripts/render.py`。

## 第 0 步 — 收集信息（只问缺失且必要的；其余先做并标注）
地址，或至少城市 + 街区 · 物业类型 · 卧室 / 卫生间 / 平方英尺 · 最多客人数 · 现在是否带家具？房况 · 停车 · 洗衣 · 空调 · 户外空间 · 有无 HOA？ · 屋主是否部分时间自住？ · 屋主目标（收入、自用、做多久、风险承受度） · 当前或预期长租房租 · 屋主承担的费用（水电、HOA、房产税、房贷——可选）。

## 第 1 步 — 合法吗？（先做这一步）
按 `ref/south-bay.md`（或用户自己的 `ref/market-*.md`） 中的清单，用网络搜索官方来源逐项核对。结论：
- **可以做** — 允许，步骤明确。
- **有条件可以** — 满足条件即可（许可证 / 房东同住 / 晚数上限 / HOA 批准 …）。
- **不建议** — 禁止或 HOA 不允许 → 改为比较中租（30+ 晚）和长租。
- **需核实** — 无法确认；列出具体问题及去哪里问。
每条规定：附来源链接 + 核查日期。绝不凭记忆陈述规定。

**工作量规则：** 如果第 1 步结论是 **不建议**，短租调研到此为止——只比较中租（30+ 晚，如允许）和长租，使用模型中的 `mtr` / `ltr` 块。

## 第 2 步 — 竞品房源（目标 8–12 个；如果每个都真实且有日期，少一些也可以）
- 同城/同区域（约 1–2 英里）、同卧室数（±0，只有凑不够时才用 ±1）、客人数和类型相近。
- 包含 2–3 个头部房源（评价/照片很好），用来展示上限。
- 每个竞品记录：链接、卧室/卫生间/客人数、评分 + 评价数、约 2–4 周后和约 2 个月后的工作日与周末价格、清洁费、最少入住晚数、关键设施、未来 30/60 天日历入住情况（估算）。记录观察日期。
- 如果打不开 Airbnb 页面，直接说明，并请用户粘贴链接 + 截图，或 AirDNA / PriceLabs 数据。不要猜价格。用户粘贴的市场数据（AirDNA 等）是有效来源——注明为“用户, AirDNA, <date>”。
- 汇总：工作日和周末平均房价（ADR）的 P25 / 中位数 / P75；入住率估算；这套房与竞品相比（更好 / 相当 / 较弱）及原因。

## 第 3 步 — 建立 12 个月预期情景
- 根据竞品 + 季节性设定每月平均房价（ADR）和入住率（South Bay 需求通常工作日以商务出行为主，夏季和活动期有高峰，12 月下旬回落——要用竞品日历和市场数据核实，不要假设）。
- 新房源：前 2–3 个月通常低于市场水平，直到积累评价——要在数字中体现或明确说明。
- 情景：保守（ADR ×0.90，入住率 −10 个百分点）、预期、乐观（ADR ×1.08，+5 个百分点），除非数据另有提示；任何调整都要说明理由。
- 只有季节平均值？对应月份用季节值，其余月份设定为使模型的**全年** ADR 和入住率与给定年度数据一致（误差约 2% 以内）；在假设中说明。
- 答案可能是中租（不允许短租，或短租收益接近长租）？请用户提供 2–3 个带家具月租竞品（Furnished Finder / Zillow furnished），填写 `mtr` 块。混合模式（旺季短租 + 淡季一段带家具中租）还要填写 `hybrid` 块（哪些月份做短租、月租金、出租月数）——模型会把所有方案并列展示。

## 第 4 步 — 成本（按本地估算，标注 估算）
每一项尽力而为：有一个可靠来源（或用户 / 屋主提供的数字）总比没有好；大项（清洁、家具、保险）用 2–3 个来源。如果某项无法快速找到来源，使用清楚标注的占位值，并放进报告的 **需报价 / 需核实** 清单——绝不当作事实呈现。
| 项目 | 方法 |
|---|---|
| 每次换房清洁（turnover） | 清洁工成本（`cleaning_cost_per_turn`），以及如有不同，用户向屋主收取的金额（`cleaning_charge_to_owner_per_turn`）——模型会显示用户的清洁差价 |
| 客人清洁费 | 接近竞品中位数 |
| 每次入住耗材 | 洗漱用品、纸品、咖啡、洗衣；按面积通常 $15–40——需核实 |
| 水电 + 网络 + 流媒体 | 有屋主账单就用；否则用本地平均值 |
| 保险 | 允许短租的保单——请屋主询价；否则给区间 + “需报价” |
| 许可证 / 登记 / 营业执照 | 来自第 1 步 |
| 维修储备金 | 收入的 5–8%（说明所选比例） |
| Airbnb 房东服务费 | 来自 `settings.md`（核实收费模式和 %） |
| 管理费 | 用户的 %（留空 → 脚本显示 15 / 20 / 25%） |
| 家具 | 如不带家具：按卧室数分两档预算（基础 / 中高档），参考 2–3 个来源；外加布置费用（拍照、智能锁、噪音传感器、安全套装、每张床 3 套床品、厨房用品、首批耗材） |

## 第 5 步 — 运行模型
`python3 scripts/str_model.py --example > in.json`，然后替换**每一个**示例值（示例不是数据）——设置 `user_lang`（用户语言，默认 zh）、`lang`（屋主语言）、`airbnb_host_fee_pct` + `airbnb_host_fee_source`（必填；来自 `settings.md`。如果设置为空，问用户一次：“Airbnb 账户是哪种收费模式、房东端费率多少？”并建议用户保存到设置中）、`needs_quote`（每个占位成本，这样会显示在屋主页面上）、`ltr`（长租房租竞品）、`mtr`（带家具月租竞品，如相关）、`furnishing.needed`；删除不适用的块。运行 `python3 scripts/str_model.py in.json`。只使用脚本输出的数字。带家具 vs 不带家具：`ltr` 块就是不带家具的方案；只有当屋主可以在两个家具预算之间选择时才运行第二次。管理费留空时，屋主页面使用中间档（20%）——要说明。
脚本还会写出 `in_owner_spec.json`（用 `lang` 语言的屋主单页）——补充 `summary` 和 `from`，可选加入风险部分，然后渲染。

## 第 6 步 — 风险（每项评 低 / 中 / 高，一行原因，一条应对措施）
法规 · 需求与季节性 · 竞争 / 新增供给 · 房屋适配度（HOA、邻居、停车、噪音、楼梯） · 运营（清洁工上门、与用户的距离） · 损坏与派对 · 财务（盈亏平衡入住率 vs 预期、回本） · 屋主匹配度（期望、自用）。

## 第 7 步 — 结论
从以下选一个：**推荐短租** · **推荐中租 (30+ 晚)** · **推荐长租** · **混合 (旺季短租 + 淡季中租)** · **不建议**。依据：首先看合法性结论；其次看屋主预期 NOI vs 长租；保守情景是否仍可接受？；屋主目标。

## 第 8 步 — 回答前自查
- [ ] 每个竞品都有链接和观察日期；每条规定都有来源和日期。
- [ ] 月度数字、合计和情景都来自脚本输出；合计一致。
- [ ] 列出假设（脚本会打印）并标注 估算。
- [ ] 如相关，带家具和不带家具都已展示；已说明回本期。
- [ ] 已展示用户自己的收入（管理费 + 清洁差价，如有）。
- [ ] 没有任何承诺——给区间，不给保证。

## 交付物
1. **给用户（对话中，用用户的语言（settings.md 里设置，默认中文））：** 结论（结论 + 一句理由）→ 收益区间表（3 个情景：入住率、ADR、总收入、屋主 NOI、用户收入）→ 逐月表 → 开支表 → 带家具 vs 不带家具 → 合规结果 → 风险表 → 竞品表（简短）→ 假设与来源 → 下一步。
2. **屋主单页（屋主的语言）：** 打开模型生成的 `in_owner_spec.json`（KPI、月度、成本和对比表已由脚本填好）。补充 `summary`（3–5 行：能不能做、预期区间、主要风险、建议），一个风险的 `sections` 项（3–5 条要点），一个关于用户做什么 + 收费 + 下一步的项，以及 `from`（来自 `settings.md` 的姓名/电话/邮箱）。运行 `python3 scripts/render.py in_owner_spec.json <name>.html`。只用区间和“估算”措辞。
3. **话术（屋主的语言）：** 6–10 句用户可以说或发送的话：核心数字区间、为什么是这套房、主要风险及用户如何管控、收费、下一步——外加对 3 个最常见异议的回答（费用太高 / 房屋损耗 / “我朋友赚得更多”）。
